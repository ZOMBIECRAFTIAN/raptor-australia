# Split Governance - v1.5

## Current Split

The v1.5 dataset uses a fixed processed split:

| Split | Images |
|---|---:|
| Train | 1,590 |
| Validation | 196 |
| Test | 206 |

This split is acceptable as a Master's baseline because it is fixed,
audited and reproducible. It should not be presented as a final
deployment-grade ecological split.

## Leakage Audit Status

The current leakage audit is generated by:

```powershell
python notebooks\audit_dataset_leakage.py --max-hamming 4
```

Outputs:

- `results/leakage_audit.json`
- `results/leakage_audit.md`
- `results/leakage_near_duplicate_pairs.jpg`

The audit checks exact file hashes, filename/source-ID reuse and dHash
near-duplicates across train/validation/test. Near-duplicate candidates
must be visually reviewed before final thesis claims.

## Master's-Level Position

For the current Master's framing:

- report the existing split honestly;
- include the leakage audit results;
- do not claim photographer/event-level independence unless richer
  metadata supports it;
- treat near-duplicate candidates as a threat to validity;
- keep the v1.5 metrics as baseline metrics, not deployment guarantees.

## Stronger v2.0 Split

For v2.0 or doctoral work, the split should be rebuilt with group-aware
rules:

1. Group by observation ID when available.
2. Group by photographer/user ID when available.
3. Group by source record or media identifier.
4. Keep all near-duplicates in the same split.
5. Recompute all metrics after the split changes.

Changing the split invalidates existing headline metrics until the model
is re-evaluated or retrained.
